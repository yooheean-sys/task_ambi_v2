## 2. 根拠

- **D09-a**: 憲章 §1 の目的はコンテキスト長（1 セッション＝1 モジュール）であり、BC-03 の ≈3,800 行＋テスト＋SKILL.md は 100k トークンを超えるので分割は必要。線は「外部依存なし（stages）／CrewAI 依存（executor）／盤面と vault の依存を持つ流れ（orchestrator）」で、テストの独立性と変更頻度が一致する。BC-01 は逆に、UC-07 が 1 つの validate（`p2_sequence_UC-07.mmd`）で全設定を横断検査するため、割ると保存経路がインスタンス相互依存になる。純粋値渡しで回避はできるが同じ集約を Protocol で縫い直す形になり、行数の利益（大 ≈2,300＋小 ≈400）も出ない。「目安超過を受容し硬い契機で再検討」は憲章 §1 自身が書く手順
- **D09-b**: LLM を呼ぶ MOD は executor 1 つで、共用でないものを common に置くのは §7-5「common を物置にしない」に反する。Interceptor の差し込み点は CrewAI `LLM(interceptor=)` の 1 箇所（Z-1）で、そこに至る型は crewai のもの。契約を httpx 型で切れば common も monitor も crewai を import せずに済み、linter (3) と両立する。`RunHalted` を BaseException 直系にするのは PoC 実測（`Exception` だと CrewAI・openai SDK のリトライに食われる。Z-6）
- **D09-c**: 読み専用の利用者（settings→board の削除ガード、monitor→board の確認読取）が書き手のスタブを持たずに済み、型で「触れない」ことが見える。提供 MOD ごとに 1 Protocol にすると board は 14 メソッドの巨大契約になり、消費者ごとに切ると同じメソッドが多重定義になる
- **D09-d**: 制約から一意（feature 間 import 禁止＋複数 BC が同じリテラルを使う）。意味論を common に置かないのは §7-5
- **D09-e**: 外側ループ・CrewAI・bd CLI は同期コードで、非同期契約にしても orchestrator 内で `to_thread` に包むだけになる。APScheduler／watchdog はスレッドベース。human 入口を orchestrator に置くのは D08-d「human 起動は BC-03 の入口が自分で組む」の実装形で、trigger の manual に統合すると DM-19 の起動種別 human を廃止する改訂（D06・D08-d）が要る
- **D09-f**: D01「起票は 1 箇所」「判定の出所は回復層と同一」を MOD 境界で保証するには、盤面を読むゲートと起票が同じ MOD（orchestrator）にある必要がある。形のゲートはプロンプトのテンプレート（提案の書式）と一緒に動くので stages。executor の依存を Tools 用に絞るのは、CrewAI 差し替え時に触る面を最小にするため
- **D09-g**: D08 の BC は「外部依存の単位」で切ったものが 3 つ（board・vault・monitor）あり、その根拠は import で機械化できる。憲章 §2 の「指定ツールはアダプタ分離・Protocol 経由のみ」の実装形
- **D09-h**: D05-c／D08-h と同じ趣旨（完了を主観にしない）。工程文書の「features 間の直接矢印なしを自己検証」の機械形
- **D09-i**: 事実の食い違いは推測で埋めず指摘する（§0-1）が、現物で確定した以上は放置する理由がない。いずれも `pocs/` の `.git` と現物ファイルで確認済み
- **D09-j**: セッション負荷の平準化。4.5 は設計メモ全体を触るセッションなので §6-1 の改訂と相性がよい
