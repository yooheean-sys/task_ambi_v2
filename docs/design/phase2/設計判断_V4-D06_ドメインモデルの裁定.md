## 2. 事実（裁定の前提として本セッションで確認したもの）

- casbin PoC: プロジェクトは `fleet.yaml` の `projects:` キーであると同時にメンバ ID の前半（`manifest.py:77, 90`）。ドメイン不使用、1 PJ＝1 policy.csv（`manifest.py:156-157`）。メンバ単位の任意 `model`＋`defaults.model`（`manifest.py:334`）だが実配線はモック固定（`loader.py:179-180`）。`AgentRegistry`（`identity.py:40`）が `agent.id`／`agent.role` → subject を張る
- renkei PoC: **プロジェクト識別子は存在しない**（`src/` に `project:` ラベルも project フィールド参照も無い）。「プロジェクト」に相当するのは three 階層の中間段 issue（`config.py:150`（`PROJECT_STAGE`））で、`outcome/<親issueID>/` がそのまま置き場（`tools.py:602-614`）。bd actor は `POC_ACTOR` 既定 `crew-exec-01`（`config.py:328`）で全 AI 共通。ペルソナ 9 種はそれぞれ PROPOSE または EXECUTE の一方にのみ属す（`personas.py:201-215`）。POC_LABEL はコード既定が空文字（`config.py:329`）で `.env.example:21` の `role:executor` と食い違う（事実として記録）
- MIN_ITEMS=2 の実害: lfg 型罠は構造由来で両モデル同型発火、deepseek は人間 5 往復でも完走不能（`PoC 完了報告 §2, §5-6`）。=2 の利益（言い換え排除）は未実測
- 工程文書「投下ファイル」の要求は AC-R12-2 の「書き込み完了後に起動」まで。消費・起票の要求は無い

## 3. 根拠

- **D06-a**: 統括が「どのプロジェクトか」を判定する（ORG-4）以上、判定結果は盤面に残す必要があり（P2）、renkei に識別子が無いため新設が要る。ラベルは既存の伝播経路をそのまま使え、システム側の対応表（issue ID→project）という固有状態を増やさない（憲章 §2）
- **D06-b**: ペルソナ→段が関数（1 対 1 の所属）なので、ID に段を持たせるのは二重宣言（P4）。casbin PoC の 2 セグメント資産を無改造で流用できる（3-4 X-6「無改造流用は不成立」は、段が導出できる事実で覆る）
- **D06-c**: 3 系統の名前空間は写像規則が無いと「人間の回答か AI の自作自演か」が判定できない（X-4）。台帳外を「人間」に倒すのは P3 の既定値フォールスルー
- **D06-d**: プロファイル化で base_url・context_window・T が 1 出所になる。既定 OpenRouter は運用の既定モデルが人間の決定（`PoC 完了報告 §4`）
- **D06-e**: 対応表は PoC が実測で確立した接合部（`loader.py` docstring）。設計として要るのは「7 種が CrewAI のどの公開機構に対応するか」であり、書式は M1 で決め直す
- **D06-f**: 構造由来の詰みは頑固に再現する（P1 適用限界）。=2 の利益が未実測で害が実測済みなら、害を除いた上で観測を残す方が P3 に沿う。段属性化はテンプレートと同じ出所（Stage）に置くこと（P4）
- **D06-g**: T はモデルの性質であり、プロジェクトの性質ではない。回数・コストは案件で予算が違いうるので PJ 上書きだけ許す
- **D06-h**: 付録・AC の要求は「起動」まで。消費まで持つと「どのプロジェクト・どの段に起票するか」の規則が別途要り、要求に無い機能が増える
- **D06-i**: bd に failed 状態が無く PoC の `state:failing` が実測済み。question を失敗にも使うと質問の意味が 2 種になり、回収層のガード（未回答の質問待ちは触らない）の前提が崩れる
- **D06-j**: (1) 間隔はトリガーの性質。(2) 憲章 §10 はアプリ内の自前復旧を禁じており、殺して回収するより完走が単純。(3) 憲章の条文どおり。(4) P3
- **D06-k**: D03-a（実行時 acceptance_criteria も定義に従う）と R#19（beads-ui に欄が無い）の帰結。穴①⑤を構造で塞げる（P1）
- **D06-l**: 粒度の規則はエンティティの形を変えず、P1 のプロンプト層かゲート層でしか実現できない

## 4. 棄却した選択肢

| 選択肢 | 棄却理由 |
|---|---|
| プロジェクトを親 issue から導出（issue ID→project の対応表をシステム側に持つ） | 固有状態が増える（憲章 §2）。ラベル伝播で足りる |
| メンバ ID に第 3 セグメント（段）／casbin ドメイン採用 | 段はペルソナから導出可（P4）。ドメインは PoC 資産と非互換 |
| bd actor は AI 共通のまま（メンバ単位 blame は履歴側で持つ） | 履歴の実体が X3 で未決。盤面（正）に主体が残らない |
| LLM 割当をプロジェクト単位のみ | レビュー別モデルが表現できない |
| hooks を設定対象から外し Interceptor に一本化 | hooks はツール呼び出しの前後の観測点で Interceptor（HTTP 層）と役割が違う。フェイルオープンの追実測は据え置きのまま |
| MIN_ITEMS 統括のみ 1・他は 2 維持 | lfg 型罠は WS 段で発火しており消えない |
| 上限を段・ペルソナ単位まで | 見積精度を上げない（D04-a） |
| ファイル投下で自動起票 | 要求に無い。規則が別途要る |
| F を question 起票でも通知 | 質問の意味が 2 種になる |
| 削除ガードを警告 | P3 |
| 起票 UI を持たない | 受け入れ条件付き起票の入口が CLI だけになる（R#19） |
| WS 粒度を今裁定（執筆 WS のソース再読解禁止をゲート化／分析＋執筆を 1 WS に統合） | 適用範囲の判定規則が別途要る／分割の利益を捨てる。いずれもテンプレート設計の中で決める方が材料が揃う |
