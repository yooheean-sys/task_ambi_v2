## 2. 根拠

- **D07-a/b**: 憲章 §2「常駐機能も永続ストアを持たない。ジョブ定義は設定ファイル宣言＋起動時再登録」の条文どおり。履歴は憲章 §4 が「ログは FS 直置き」を許しており、追記のみ・表示専用なら「システムが所有する永続ストア」ではなくログと読める。付録の SQLite 2 箇所（jobstore・別テーブル）はいずれも憲章と衝突していた（05 UC-09/10 の食い違い 2 点）
- **D07-c**: OB-12 の要求文言（obsidian タイトル・windows-mac 互換性のない文字）そのもの。Windows 側で作れないファイルは Dropbox が黙って同期エラーにする（OB-13）ため P3 上ゲートで弾く
- **D07-d**: ユーザ裁定。フォームの利点（R#19 の回避・穴①⑤の構造塞ぎ）より、UI を 1 つ増やさない方を採る。受け入れ条件付き起票は CLI で成立する（`bd update --acceptance`、PoC 完了報告 §3 ②）
- **D07-e**: 二段判定は「誰が（Casbin・改訂可）」と「何が安全に実行できるか（ALLOWED・許可リスト）」の性質の違い。CRUD 化は「構造→ゲート」への格下げに見えるが、AI 到達不能な置き場という別の構造に保証を移せば同等。両方が設定側に揃うことで、現行では検出されない「policy にあって ALLOWED に無い」ずれを validate 1 箇所で突合できる（P4）。憲章 §7-4「調整可能なパラメータは設定に外出し」とも整合
- **D07-f**: ユーザ裁定（メンバは手動で作る運用）。テンプレートは「登録時にどのペルソナのメンバを作るか」の出所でしかなく、手動作成なら不要。kind は導出先が無くなるので残すと死に属性（P4）
- **D07-g**: ユーザ裁定「beads は AI タスクを整理する場所」。登録操作は人間と設定 UI の間で完結し、AI タスクの状態ではない。kickoff 時は Streamlit セッションが無く issue は claim 済みなので、進めない理由を盤面に残さないと無症状停滞（穴①と同型）になる

## 3. 棄却した選択肢

| 選択肢 | 棄却理由 |
|---|---|
| jobstore を SQLAlchemyJobStore（付録 §1） | 憲章 §2 と衝突。取り逃しの追い発火も持たない方針 |
| 履歴を bd コメント／vault に委ねる（05 UC-10 の案） | 盤面・vault は AI タスク／成果物の場所。運用ログを混ぜない |
| 禁止文字を Windows 集合のみ | Obsidian タイトル禁止文字で wikilink が壊れる（OB-12 の要求に不足） |
| 起票フォームを持つ（D06-k） | ユーザ裁定で不要 |
| ALLOWED をコードのまま | 変更にコード改修が要り、policy との突合が validate で書けない |
| ALLOWED を AI 到達可能な設定領域に置く | AI が自分の実行可能集合を広げる経路ができる（P1 の保証を失う） |
| 組織テンプレートを維持／登録時に全ペルソナを自動生成 | ユーザ裁定（手動作成）。自動生成は不要メンバの削除作業を生む |
| kickoff 時のエラーも beads に書かない | 盤面上は claim 解放だけになり無症状停滞（P3） |
