# 設計判断 V4-D03: 受け入れ条件の定義の採用

**裁定日**: 2026-08-18
**論点の出典**: 付属規約「受け入れ条件の定義」（2026-08-17 起草）§8 の ★1・★2、および同定義の適用開始にあたっての単位・範囲
**レジーム**: append-only（§0-4）。本記録は裁定済みの判断のみを置く

## 1. 裁定

| # | 論点 | 裁定 |
|---|---|---|
| D03-a | 定義の適用範囲（★1） | **(b)** 文書上の要求（設計メモ §2・D シリーズ）に加え、**実行時に bd issue へ書く acceptance_criteria も本定義に従う** |
| D03-b | 完成済み §2 への遡及（★2） | **適用する**。§2 の各要求を (1) 受け入れ条件化 (2) H 等級化 (3) 保留枠＋解除条件 のいずれかに仕分ける。要求の追加・削除はしない |
| D03-c | 仕分けの単位 | **§2「2. やりたいこと」の項目単位**（R-01〜R-13）。フェーズ1 の UC-nn は対応表で紐付けるのみで、UC 自体を単位にしない |
| D03-d | 対象範囲 | **システム要求（V4 到達点 = D02-a のスコープ）のみ**。M1（リファクタの挙動不変）・M2（トリガー導入）の完了判定基準は含めない（§6-1 注記のとおり M1 設計時に別途定義） |

**採用する形（1 行）**: 定義本文は `docs/initial_memo/付録：受け入れ条件の定義.md`（改訂可）、仕分け結果は `outcome/design/phase1/06_acceptance_criteria.md`（改訂可）に置き、§2 側には各項目の印（等級／H／保留／対象外）だけを付ける。

## 2. 根拠

- **D03-a**: 「第三者（AI 含む）が実行して判定」は close ゲートの動作そのもの。文書と実行時で定義を分けると同じ概念に 2 つの規格ができる（P4）。既知の制約（beads-ui から acceptance_criteria を入力できない R#19、`poc lint` は形しか見ない R#29）は実現方式であり、lint 拡張・書式は設計論点として作業メモへ登録する
- **D03-b**: §2 は本定義の主対象であり、書いた直後の今が変換の最安時点。仕分けは「各要求に印が付いていること」を成功基準として 1 セッションで完了できる
- **D03-c**: UC 単位は粒度が検証単位に近い利点があるが、§2 の要求文を単位にしないと §2 への印付け（遡及の成果）が間接的になる。UC の前提・主フロー・事後条件は 4 要素の素材として使う
- **D03-d**: M1 完了判定は「テスト全緑は移行の正しさの観測であって設計の正しさの合否ではない」（§6-1 注記・P3 適用限界）という別種の問いを含み、M1 の境界設計と同時でないと観測点が定まらない

## 3. 棄却した選択肢

| 選択肢 | 棄却理由 |
|---|---|
| (a) 文書上の要求のみに適用 | 実行時 issue の close ゲートと文書の受け入れ条件が別規格になる（P4） |
| 遡及しない | §2 の要求が無印のまま残り、定義 §9 の自己適用が偽になる |
| UC 単位で書く | §2 への印付けが間接化する。UC の粒度は 06 の条件 ID（AC-Rnn-k）で表現できる |
| M1/M2 完了判定も同時に書く | 観測点が M1 の境界設計に依存し、定義 §6 の「未決境界に依存しない」に抵触する |

## 5. 本裁定が決めていないこと

1. スコープ裁定で対象外となった §2 記述（GitLab・D02-b）に付ける印を第 4 区分 (iv) として認めるか（定義 §9 ★3。R-13 の仕分け時に裁定）
2. 実行時 acceptance_criteria に等級・観測点をどう載せるか（書式）と、それを検査する lint 拡張の設計（§5 論点）
3. 保留枠の解除条件が成立したときに誰が再仕分けするか（運用手順）
