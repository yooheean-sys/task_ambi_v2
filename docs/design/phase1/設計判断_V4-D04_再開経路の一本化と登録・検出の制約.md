# 設計判断 V4-D04: 再開経路の一本化と登録・検出の制約

**裁定日**: 2026-08-18
**論点の出典**: 第一フェーズ成果物の読み合わせ（三層リトライの積／X-3 戻り値の非信頼／未決 E6／UC-08・09 の CRUD）に対するユーザ確認 4 点
**レジーム**: append-only（§0-4）

## 1. 裁定

| # | 論点 | 裁定 |
|---|---|---|
| D04-a | UC-12 の上限値の見積もり | **三層リトライの積**（openai SDK × CrewAI × executor iterations）で見積もる。1 つの論理的失敗が最悪何リクエスト・何トークン・何円に化けるかを積で計算してから上限を決める。上限を厳しくするなら外側の回数を絞るのではなく内側の層を縮める（確認。図・メモに既記載） |
| D04-b | UC-13 の bd 側の信頼性 | bd への写像後に**確認読取**（`bd show`／`bd comments`）で盤面への反映を検証する。rc は見ない。不一致または bd 不達なら黙って進まず**停止**し、ローカルログに痕跡を残す（P3） |
| D04-c | 人間回答後の再開経路（未決 E6） | `--watch` モードを**廃止**し、再開の起点を **interval 既定トリガー「ready 巡回」**（常設・間隔は設定値・UC-09 で間隔と有効/無効のみ変更可）＋手動実行の 1 系統に一本化する。待機中の元 issue は claim 解放済み・open + blocks（既存実装）。回収層の「未回答の質問待ちなら触らない」ガードは crash window 用に維持。E6 は解消 |
| D04-d | UC-08 の責務と制約 | UC-08 は**フォルダ対応付けの登録・編集・削除のみ**。フォルダ実体の作成・改名・削除は人間が手動で行う。**kickoff 時に対応フォルダの存在を検証**し、無ければ停止して理由を残す。**削除時に当該プロジェクトの open issue があれば拒否または警告**する |
| D04-e | UC-08 / UC-09 の名称 | CRUD を明記（「プロジェクトを CRUD する（フォルダ対応付け）」「トリガーを CRUD・有効化・手動実行する」） |

## 2. 事実の訂正（D04-c の前提）

対話中に「PoC はエスカレーション時に親 issue の claim を握ったまま待つので、claim を解放し blocks 依存で待たせる形に変える」と説明したが、**現物は既にそうなっている**。

- `crewai_beads_renkei _open_escalation` は **create → dep → release** の順で、コメントに「in_progress のままだと ready にも blocked にも出ないので claim を解除する」と明記（PoC 基準版）
- `--watch` は「ready が空でも未回答の質問が残る限りループを終了せず `bd ready` を見続ける」**ループの終了条件のモード**であり、issue をプロセス内で保持する仕組みではない（loop.py:139-172, 1657-1697）
- 回収層の「未回答の質問待ちなら触らない」（loop.py:1003-1007）は、create→dep→release の途中でプロセスが死んだ窓のための安全策（`_open_escalation` docstring）
- ユーザ作成の `06_acceptance_criteria.md` AC-R03-3「close で元 issue が ready に現れる」はこの実装と整合している

したがって D04-c の実体は「claim 解放への変更」ではなく「**watch モードの廃止と、再開起点の ready 巡回への一本化**」に限られる。

## 3. 根拠

- **D04-a**: 各層は他層のリトライを知らないため、失敗 1 件に対する実リクエスト数は各層の回数の積になる（`crewai_ai_control` P3 実測、7-2 E）。外側ループに再試行を足せば 4 層目になり、さらに掛かる（P2 適用限界）
- **D04-b**: X-3 の主張は「両方成功が必要」ではなく「**戻り値で成功を判定するな、状態を読め**」。bd 複数 ID close の部分失敗で rc=0（R#4）、stderr は恒常ノイズ（R#18）のため、写像の成否は読み直しでしか分からない。bd 自体が壊れているときは bd に乗せられないので、停止と別経路の痕跡が要る
- **D04-c**: E6 の衝突は「質問で止まっている issue」と「トリガー待ちの issue」の区別の問題ではない（区別は blocks 依存の有無で既にできる）。衝突が起きるのは質問 close 直後で、watch ループと新規起動ループの**両方が正当に再開してよい**状態になるから。再開の所有者を 1 つにすることが解であり、常駐 daemon の interval トリガーが watch の「待って拾う」役割を代替できる。P2（進行状態は盤面に）・P4（再開の出所を `bd ready` 一つに）に沿い、プロセスの生死に依存しない
- **D04-d**: constitution §2「外部ストアには本システム以外の書き手を常に想定する」に沿い、システムは vault の構造を所有しない。手動管理を前提にする以上、登録時検証だけでは改名・削除に追随できないため実行時検証が要る（P3: 空コンテキストで黙って走らせない）。beads 側の issue は残るため、参照先の無いプロジェクトを作らない削除ガードが要る
- **D04-e**: 付録：トリガー §5 に「トリガー CRUD」と明記があり、プロジェクトも対応付けの編集・解除が要る

## 4. 棄却した選択肢

| 選択肢 | 棄却理由 |
|---|---|
| トリガー実行側の issue にタグを付けて区別する | 区別は既に可能で問題の所在が違う。静的なタグは kill -9 で剥がせず、回収層が「他人が持っている」と読めば無症状停滞（穴①と同型）。生存状態を反映しない印で所有権を表すのは P1 の最下位 |
| 既存 PID ロックをトリガーにも効かせ共存を禁じる | 人間の回答待ちの間ほかのトリガー実行がすべて止まる |
| watch を残し回収層側で避ける | 再開の所有者が 2 つ残る（P4 の二重宣言） |
| UC-08 でフォルダ実体も CRUD する | vault の所有権をシステムが持つことになり constitution §2 に反する |
| UC-08 の存在検証を登録時のみにする | 手動改名・削除に追随できず、空コンテキストで黙って走る（P3） |
