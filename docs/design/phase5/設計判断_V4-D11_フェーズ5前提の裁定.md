## 2. 根拠

- **D11-a**: 構築順は依存の一方向性（p4 notes §4）に沿うので、提供 MOD の受け渡し型が利用 MOD より先に確定し手戻りが出ない。stages を先頭にしても同じ性質は満たすが、ユーザは composition root と同じ順で追える方を選んだ
- **D11-b**: 図・csv の短文の正本として notes を置くのは D05 以来の型。mermaid は 1 ファイル 1 図なので、入口が複数ある MOD（settings＝UC-07/08＋実行時解決、orchestrator＝周回＋recover＋human 起動、trigger＝発火＋CRUD）を 1 図に詰めると 100 行超で読めない
- **D11-c**: 「モジュール内部のシーケンス」という工程文書の趣旨に応えるには service／adapter の境界が図に出る必要がある。ファイル単位は憲章 §3 が既に定めた粒度で、クラス・関数単位まで割ると M1 のファイル分割で壊れる。ライブラリを内部レーンにするのは linter (3)（crewai→executor のみ 等）が図で検証できるため
- **D11-d**: 型の属性は提供 MOD の設計と同時に決まる（例: `Issue` は board が bd JSON から何を写すかで決まる）。共通ファイルに集約すると MOD ごとのレビューで毎回 common 側を書き足すことになる。kernel は MOD でないが正本が要る（ラベル語彙は 4 MOD が使う。D09-d）
- **D11-e**: MOD ごとの採番は作成順に縛られず、後から board に fn を足しても番号が飛ばない。P2 の FN は MOD 分割前の粒度なので 1:1 にならないのは前提。被覆条件を機械化しないと「実装されない FN」が無症状で残る（P3）
- **D11-f**: composition root（apps/api）が 8 通りの戻り値を扱わずに済む。ui ページを handle に載せると apps/api プロセスが streamlit ページ関数を保持することになり linter (3)（streamlit は ui.py と apps/ui のみ）と衝突する
- **D11-g**: D05-c／D08-h／D09-h／D10-g と同型（完了を主観にしない）。(ii)(iii) は工程文書の「他モジュールは Protocol 名のレーン」「依存する if_id」を機械化したもの
- **D11-h**: D10-f と同型（二重記載を避ける P4）。8 MOD＋common で 1 セッションに収まらない（作業メモ A-0）ため handoff を MOD 単位で刻む
- **D11-i**: 事実の食い違いは推測で埋めず指摘する（§0-1）。憲章の適用は D10-d でユーザ作業と定めた
