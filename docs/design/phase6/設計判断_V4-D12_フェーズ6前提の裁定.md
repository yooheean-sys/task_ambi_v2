## 2. 根拠

- **D12-a**: 付3（.env／config の洗い出し）と付2（テストダブルの特定）が `p6_external_interface.csv` を INPUT にするので、自システム所有の FS と観測出口も行にしておく方が後工程で拾い直さずに済む。種別は EXT 表の列で区別できる。工程文書の食い違い（`p3_context_map.csv`・`EXT-*` の不在）は推測で埋めず §0-1 どおり指摘し、正本を新設した
- **D12-b**: 「何とどう繋がるか」が 1 行で読め、行数 13 で一覧性を保てる。相手×MOD だと .env・config.json・LLM で行が増え認証・失敗時の記述が重複する。相手×Protocol は p4 契約 csv（IF-nn）と二重記載になる
- **D12-c**: 第5 の 3 MOD と DEC-015 が「API Contract の正はフェーズ6」と送っており、テキスト表では DTO の構造が落ちて M1 で起こし直しになる。OpenAPI は FastAPI の生成物と機械で突き合わせられる
- **D12-d**: ユーザの将来要求（CLI 型バックエンド）を設計文書に痕跡として残す価値がある一方、crewai 型を契約に出せない制約（linter (3)・憲章 §7-2）から切替点は executor 内部にしか置けない。したがって「Y＝Protocol 経由の確認」は差し込み点（Hook）と切替点（LlmFactory）の 2 点で読む。憲章の字面（指定ツール＝beads のみ、HTTP 前提）とは差分が出るので PATCH として提示し、適用可否はユーザに残す（D10-d）。CLI 型の実装は monitor・executor の承認済み成果物を開け直すことになり第6 の範囲を超える
- **D12-e**: 憲章 §6「ヘルスチェック必須」を満たす最小形。apps は業務ロジックを持たない（憲章 §3・§4）ので外部ツールの到達性を見に行かない。可用性対策は対象外（§10）
- **D12-f**: 工程文書「単一プロセス内のモジュール配置と、外部ツール・ファイルシステム・スケジューラとの関係を 1 枚で」に、`01_context.mmd` と同じ Boundary（WSL2／Windows 側／外部サービス）を重ねると L1→配置図が読み継げる。POST /hooks/file の発信元とブラウザの居場所が図に出る
- **D12-g**: D05-c／D08-h／D09-h／D10-g／D11-g と同型（完了を主観にしない）。裁定が 7 件なので decision_log を別に持つと二重記載（P4）

## 4. 事実（裁定ではない）

- 工程文書（設計工程の手順書）は 2026-08-19 時点で同名で実在（`ls` で確認）。第6フェーズ節の INPUT／OUTPUT は handoff_p5 §2 の記載と一致。ただし INPUT の `p3_context_map.csv` は存在せず（phase3 の対応物は `p3_bc_ownership.csv`）、`EXT-*` はどの成果物にも未定義だった（`01_context.mmd` は C4Context の alias `beads`／`beadsui`／`vault`／`dlfolder`／`llm` のみ）
- settings-F17（feature_list）は `global/humans.yaml` を CRUD すると書いているが、F21 の router 列挙（8 リソース）に `/settings/humans` が無かった → openapi に追加し、p5 csv F21 概要を本フェーズ末に改訂（`_変更履歴.md` に記帳）
- openapi を書く際に決めた細部（D12-c の範囲内）: (1) rules は PJ 共通と役割ルールの 2 種があるため `/settings/rules/projects/{project_key}`・`/settings/rules/roles/{persona_key}` に分けた（1 段 `/settings/rules/{x}` は `roles` と project_key が衝突し得る）(2) プロジェクト削除ガード（open issue あり・盤面不達・`_program`）は validate 違反ではなく現在状態との衝突なので **409** を追加（F21 の語彙 422/404 に加わる）。トリガーの既定削除不可は validate 扱いで 422 のまま (3) LLM プロファイルの既定は `LlmProfileSpec.is_default` で切替（別パスを持たない）(4) `GET /kickoffs/current` は無ければ 200 `{running:false, record:null}`（404 にしない）
- 配置図は最初 `flowchart TB` で描いたが、nested subgraph の `direction` が外向き辺で無視され横一列（幅 2,400px 超）に潰れた。**`LR` にすると MOD 列→ストア列→外部サービスが左→右、Windows 側が下段に並び読める**（mmdc で実測。作業メモ E 節の「LR は横に伸びすぎる」は subgraph 構成次第で逆になる）。subgraph を辺の端点にすると内部 direction が無視されるため、.env／config.json と stdout の辺は代表ノード（apps/api・common）を端点にした
- `python3 p6_selfcheck.py --render` → ERRORS: none（csv 13 行・EXT 13・Protocol 14・openapi 25 paths／48 operations／42 schemas。PyYAML 6.0.1 あり。PyYAML 無しの最小パーサ経路も ImportError を偽装して動作確認）
- PoC 無変更: セッション開始時 `git -C pocs/<repo> status --porcelain | grep -v '^??'` は renkei `D` 5 行・casbin `D` 3 行（作業メモ D-5 の事前状態）
- PoC 由来の参照は本フェーズでは新たに引いていない（入力は全て第3〜第5 成果物と憲章）

4. **`POST /hooks/file` の発信元検証**: 憲章 §10 により置かない。localhost 以外から叩かれる構成になったら再提起
5. **openapi の DTO 細部**（任意項目・既定値・文字列の正規表現）: M1 で schemas.py を起こすときに詰める。paths・method・応答コードは本書が正
